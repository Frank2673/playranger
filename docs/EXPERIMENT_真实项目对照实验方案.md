# PlayRanger 真实项目对照实验方案（量化效率提升）

> 目的：把「AI 自动试玩比人工更快」从主张变成可复核的数据。
> 对应不足：验证层「缺少与人工测试的对照基线（漏报率、误报率、节省工时）」。
> 定位：本方案不追求统计显著性，追求**可复现的对照流程 + 可逐条核对的原始数据**。小样本下宁可报区间与效应量，不硬套 p 值。
> 专项实例：针对真实第三方游戏 2048 的可执行版本见 [`EXPERIMENT_2048_真实项目对照实验方案.md`](EXPERIMENT_2048_真实项目对照实验方案.md)（10 个注入缺陷 × 三组 × 3 轮 + 工具/人工定位对照）。

---

## 一、待验证假设

| 编号 | 假设 | 判定口径 |
|---|---|---|
| H1 | 同等投入下，PlayRanger 的缺陷发现率不低于人工探索 | 发现率差值 ≥ -5 个百分点 |
| H2 | PlayRanger 的缺陷定位信息完整度高于人工报告 | 证据完整率 ≥ 90%，人工 ≤ 50% |
| H3 | PlayRanger 的单缺陷平均耗时低于人工 | 耗时下降 ≥ 30% |
| H4 | PlayRanger 误报率处于可接受区间 | 误报率 ≤ 20% |
| H5 | 缺陷可稳定复现 | 抽样回放复现成功率 ≥ 80% |
| H6 | 接入成本足够低 | 从零到首份报告 < 0.5 人日（Web 游戏） |

> 反假设（必须一并报告）：若 H3 不成立，需说明是否因「人工测试者熟悉该游戏」导致基线偏高；若 H4 超阈，需给出误报的异常类型分布。

## 二、实验设计

### 2.1 被试材料（3 个游戏，覆盖不同感知难度）

| 编号 | 类型 | 技术特征 | 选它的理由 |
|---|---|---|---|
| G1 | DOM 回合制/卡牌（自研） | 状态全在 DOM，可接 SDK | 精确模式基线，验证零脚本主链路 |
| G2 | Canvas 平台跳跃（开源改造） | DOM 无状态，需视觉 | 验证盲测模式与 Canvas 可读性上限 |
| G3 | 含随机数与动画时序（自研） | 随机掉落、动画未结束可点击 | 验证回放确定性与时间敏感缺陷 |

要求：三个游戏均**可注入缺陷**且**可重置到同一初始状态**（存档/刷新）。

### 2.2 缺陷注入（每个游戏 10 个，共 30 个）

每个游戏预埋 10 个已知缺陷，与自然出现的缺陷混合（不告知测试者哪些是埋点），分布如下：

| 类别 | 数量/游戏 | 示例 | 预期主要发现通道 |
|---|---|---|---|
| 状态类 | 4 | 重开后血量未重置；分数与实际不符；场景切换后道具残留；关卡计数错位 | SDK 状态比对 / 断言 |
| UI 类 | 3 | 文本溢出容器；按钮点击无响应；数值显示与内部状态不一致 | 视觉检测 / DOM 校验 |
| 交互类 | 2 | 连点导致重复结算；动画中点击被吞 | 动作轨迹 / 断言 |
| 隐蔽型 | 1 | 需 3 步以上组合触发（如「先买再退再进关」才出错） | 多通道聚合 |

埋点规范：
- 每个缺陷登记 `defect_id / 触发路径 / 期望行为 / 实际行为 / 严重度真值`；
- 触发路径写成可执行步骤（供仲裁者复核）；
- 隐蔽型必须由第三人按路径手工复现一次，确认可触发后才计入分母。

### 2.3 分组

| 组 | 配置 | 投入上限 | 说明 |
|---|---|---|---|
| A 人工探索 | 2 名有 1 年以上测试经验的测试者，各自独立 | 每人 90 分钟 | 允许查文档、允许提 Bug 单；不提供埋点信息 |
| B PlayRanger | 1 次自动跑测 + 人工复核 | 机时 90 分钟 + 复核 30 分钟 | 固定模型版本与温度；目标描述统一 |
| C 协同（可选） | PlayRanger 报告交给 1 名测试者复核补充 | 工具 90 分钟 + 人工 60 分钟 | 验证「工具当前置筛子」的增量价值 |

### 2.4 样本量与轮次

- 每个游戏 × 每组 × 3 轮（共 3 × 3 × 3 = 27 个实验单元；C 组可选则 +9）。
- 轮次间必须重置游戏到初始状态、清空 PlayRanger 记忆库（避免跨轮经验泄漏）。
- **顺序随机化**：同一游戏的 A/B 顺序在轮次间交替（缓解学习效应）。

### 2.5 对照与盲评

- 人工组不知道埋点清单；PlayRanger 组也不注入埋点信息（只给目标）。
- **仲裁**：两名未参与测试的评审独立判定每条报告的缺陷是否「真实、可复现、非重复」，分歧由第三人裁决。
- 一致性要求：Cohen's Kappa ≥ 0.6；低于 0.6 需重新定义判定标准后重评。

## 三、指标定义与计算公式

| 指标 | 公式 | 说明 |
|---|---|---|
| 发现率 | 被判定为「已发现」的埋点缺陷数 ÷ 埋点缺陷总数 | 「已发现」= 描述可对应到该埋点，不要求措辞一致 |
| 误报率 | 仲裁为无效的缺陷数 ÷ 报告缺陷总数 | 无效含：不存在、不可复现、重复、把设计当缺陷 |
| 漏报率 | 1 − 发现率 | 与发现率互补，报告中同时列 |
| 严重度加权发现分 | Σ(权重 × 已发现数) ÷ Σ(权重 × 埋点数)，权重 blocker=5/critical=4/major=3/minor=2/info=1 | 防止「只抓小问题」刷高发现率 |
| 单缺陷耗时 | 总投入（人时 + 机时折算）÷ 有效缺陷数 | 机时按 1:1 折人时需在报告中声明 |
| 证据完整率 | 具备「截图 + 触发步 + 字段级差异」三要素的缺陷数 ÷ 有效缺陷数 | 人工报告通常只有文字，此项差距最大 |
| 复现成功率 | 回放三次中 ≥2 次重现的缺陷数 ÷ 抽样缺陷数（每游戏抽 5 条） | 三态：reproduced / partial / not_reproduced |
| 修复可用率 | 仲裁认为「根因排序合理且验证清单可执行」的缺陷数 ÷ 抽样缺陷数 | 仅评 PlayRanger，5 分制 ≥3 分算可用 |
| API 成本 | 步数 × 单步 token 成本 + VLM 调用次数 × 单次成本 | 单价按实际账单填入，报告须附账单截图 |

> 成本口径必须在报告首页声明：人时是否含准备时间、机时如何折算、API 费用是否含重跑。

## 四、执行流程（SOP）

### 阶段 0：准备（一次性，约 4 小时）

1. 冻结三个游戏版本，打 tag；
2. 注入 30 个缺陷，登记 `defect_manifest.json`（含触发路径与真值）；
3. 第三人手工复现全部 30 个埋点，剔除不可触发的，重新凑齐数量；
4. 固定环境：同一台机器、同一浏览器版本、同一模型版本与温度、同一视口；
5. 打印/准备评分表，培训 2 名仲裁者统一判定标准（给 3 个示例各判一次对齐）。

### 阶段 1：单轮执行（约 5 小时/游戏）

```
T+0     重置游戏 + 清空 PlayRanger 记忆与缺陷目录
T+0     启动人工组（2 人并行，各 90 分钟，全程录屏）
T+0     启动自动组（后台跑，目标与人工组一致，如「通关第一关」）
T+90    人工组停止，收 Bug 单；自动组停止（或跑满 90 分钟）
T+90    自动组人工复核 30 分钟（只允许确认/否决/合并，不允许新增）
T+120   回放抽样 5 条缺陷，记录三态
T+150   导出两份数据：人工 Bug 单、PlayRanger 报告 + 原始 defect.json
T+150   仲裁双评，记录分歧
```

### 阶段 2：数据整理（每游戏 1 小时）

把两侧发现的缺陷对齐到 `defect_manifest`，逐条标记：命中哪个埋点 / 是否误报 / 证据三要素是否齐。

### 阶段 3：复算与撰写（约 1 天）

按公式复算所有指标，输出实验报告。

## 六、统计分析口径（小样本，不夸大）

1. **主报告**：每指标给「3 轮 × 3 游戏的均值 + 最小值~最大值区间」，不做单点结论；
2. **配对比较**：同游戏同轮次内比较 A/B，报告差值分布与相对变化百分比；
3. **效应量**：用相对提升（如「单缺陷耗时下降 42%」）而非 p 值；若样本允许（n≥8 对），可附 Wilcoxon 符号秩检验作为补充，并注明样本量局限；
4. **必须报告反例**：哪些游戏上工具劣于人工（如纯主观体验类缺陷），并解释原因；
5. **不得外推**：结论限定在「Web 游戏 + 本次三个被试 + 本次模型版本」，不写「适用于所有游戏」。

## 七、成本核算模板

```
单次跑测成本 = 步数 × 单步 LLM 成本 + 截帧数 × 单次 VLM 成本 + 机时折旧
单缺陷成本   = 单次跑测成本 ÷ 有效缺陷数
节省工时     = 人工组单缺陷耗时 − 工具组单缺陷耗时（均折算人时）
投入回收点   = 工具接入成本 ÷ 单位缺陷节省工时
```

填入实际账单后，报告须回答一句：**「跑多少次可以把接入成本赚回来」**。这是独立开发者最关心的数字。

## 八、偏差控制与风险

| 风险 | 影响 | 控制手段 |
|---|---|---|
| 学习效应（A/B 顺序） | 后跑的一组更容易 | 轮次间交替顺序；每轮重置状态与记忆 |
| 人工测试者经验差异 | 基线波动大 | 固定 2 名同经验档测试者；跨游戏轮换 |
| 埋点被「认出来」 | 人工组作弊式全命中 | 埋点与自然缺陷混合；埋点路径不写入任何可见文档 |
| 隐蔽型不可触发 | 分母虚高 | 阶段 0 由第三人手工复现后才计入 |
| VLM 抖动 | 工具组结果不可复现 | 固定模型版本与温度；同轮重跑一次取并集（须在报告中声明） |
| 人工 Bug 单描述模糊 | 无法对齐埋点 | 仲裁者按「行为一致」而非「措辞一致」判定，并记录依据 |
| 只抓小问题刷发现率 | 结论失真 | 必须同时报「严重度加权发现分」 |
| 测试环境差异 | 复现失败归因错误 | 全程同一机器同一浏览器，记录版本号 |

## 九、预期产出

1. **实验报告**（Markdown + 离线 HTML）：假设逐条结论、指标表、反例分析、成本回收点；
2. **原始数据包**：`defect_manifest.json`（真值）、两组缺陷包、回放记录、仲裁表、API 账单截图；
3. **一句话结论模板**（数据出来后填空，不预先编造）：
   > 在 3 个 Web 游戏、3 轮对照中，PlayRanger 的缺陷发现率为 __%，人工为 __%；单缺陷平均耗时由 __ 人时降至 __ 人时（下降 __%）；误报率 __%；抽样回放复现成功率 __%；工具接入成本 __ 人日，约 __ 次跑测可回收。

> 写作纪律：报告首页先写「本次实验不能证明什么」（样本量小、仅 Web 游戏、仅单一模型版本），再写「能证明什么」。这样评审更愿意相信后面的数字。

## 十、最小可行版本（如果只有 2 天）

砍掉 G3 与 C 组，只做 **G1 + G2 × A/B × 2 轮**，指标保留 5 项（发现率、误报率、单缺陷耗时、证据完整率、复现成功率）。

产出仍然成立：有对照、有原始数据、有反例、有成本回收点。**宁可小样本做扎实，不要大样本做糊。**
