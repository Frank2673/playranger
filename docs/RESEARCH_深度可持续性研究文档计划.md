# PlayRanger 深度可持续性研究文档计划
## AI Agent + 游戏自动化测试 — 长期研究议程

> **文档定位**：本文件是 PlayRanger 项目的长期研究议程规划，不是产品功能路线图。
> 目的是建立 PlayRanger 在「AI + 游戏测试」交叉领域的技术深度与研究话语权。
>
> **版本**：v0.1  
> **日期**：2026-11-23  
> **状态**：规划中

---

## 一、为什么需要研究议程

PlayRanger 目前是一个工程性项目——把 LLM、浏览器自动化、游戏测试经验组合在一起，做出了一个能用的工具。

但工程组合的护城河是浅的。别人只要有同样的想法、用同样的模型，很快就能复现。

**深度护城河来自研究**：
- 有自己的基准测试 → 别人想比较，就得用你的基准
- 有自己的方法论 → 别人做这个领域，就得参考你的框架
- 有公开的研究成果 → 建立技术品牌和可信度

本文件规划 6 个研究方向，每个方向都有明确的问题、产出和时间估计。

## 三、各研究方向详细规划

### R1：游戏 AI Agent 基准测试（Game Testing Benchmark）

**研究问题**：
> 如何构建一个标准化的基准测试套件，客观评估不同 AI Agent 在游戏测试任务上的能力差异？

**为什么重要**：
- 现在各家都在自己的 Demo 上演示，无法横向比较
- 没有基准就没有进步——大家都说自己好，但没有统一的度量
- 如果 PlayRanger 能推出社区公认的基准，就掌握了这个领域的话语权

**研究内容**：
1. **游戏选择**：5-10 个开源 Web 游戏，覆盖不同类型（益智、动作、策略、休闲）
2. **缺陷预埋**：每个游戏预埋 10-20 个已知缺陷，覆盖不同类型（逻辑、UI、性能、边界）
3. **指标定义**：
   - 发现率（Recall）：发现了多少预埋 Bug / 总预埋 Bug
   - 误报率（False Positive Rate）：报告的 Bug 中不是真 Bug 的比例
   - 平均定位时间（Mean Time to Detect）：从开始到发现 Bug 的平均步数/时间
   - 复现成功率（Reproducibility Rate）：同一 Bug 重复测试能稳定复现的概率
   - 覆盖率（Coverage）：探索了多少状态/场景/代码分支
4. **统一接口**：定义 Agent 接入标准，任何 Agent 只要实现几个接口就能跑基准
5. **排行榜**：公开排行榜，定期更新

**里程碑**：
- M1（1月）：选定 3 个游戏，每个埋 5 个 Bug，做出初版基准
- M2（2月）：完善指标体系，实现自动化评估脚本
- M3（3-6月）：扩展到 10 个游戏，发布 v1.0，建立公开排行榜

**风险与挑战**：
- 预埋 Bug 太简单 → 区分度不够；太难 → 没人能发现 → 排行榜没意义
- 不同类型游戏的 Bug 分布差异大，如何加权？
- 维护成本：游戏更新后预埋 Bug 可能失效

**与产品的关系**：
- 基准本身就是 PlayRanger 的「测试用例库」
- 每改进一版 Agent，跑一次基准，量化进步
- 对外 benchmark 是最好的技术品牌建设

### R2：游戏状态空间高效探索

**研究问题**：
> 游戏状态空间巨大（组合爆炸），AI Agent 如何在有限步数内最大化缺陷发现概率？

**为什么重要**：
- 现在的 ReAct 探索是偏随机的——找可点击元素、点、观察、再点
- 对复杂游戏来说，随机探索效率极低，大部分状态根本走不到
- 如果能提高探索效率，同样步数下发现的 Bug 数量可以翻倍甚至更多

**研究内容**：
1. **探索策略分类**：
   - 随机探索（baseline）
   - 启发式探索（基于元素类型/位置的优先级）
   - LLM 引导探索（"这个游戏应该怎么玩？先试试这些操作"）
   - 强化学习探索（训练专门的探索策略）
   - 代码引导探索（静态分析标出高风险区域，优先探索）
2. **状态表示与相似度**：
   - 如何定义"两个游戏状态相似"？（DOM 相似度？截图相似度？状态向量？）
   - 相似度阈值如何设定？
   - 探索过程中如何避免重复访问相似状态？
3. **探索-利用权衡**：
   - 什么时候该深入探索一个区域（利用），什么时候该换个区域（探索）？
   - 这个决策如何动态调整？
4. **多 Agent 协作探索**：
   - 多个 Agent 并行，如何分工避免重复劳动？
   - 探索者 Agent + 验证者 Agent 分工是否更高效？

**实验设计**：
- 控制变量：相同步数、相同游戏、相同缺陷集
- 比较不同探索策略的发现率曲线（步数 vs 累计发现数）
- 统计显著性检验

**里程碑**：
- M1（2月）：实现 3 种基础探索策略，搭建实验框架
- M2（4月）：完成初步对比实验，产出第一篇技术报告
- M3（6-12月）：深入研究 RL 探索或代码引导探索，争取产出论文级成果

**风险与挑战**：
- 不同游戏的最优策略可能不同，没有通用最优解
- RL 训练需要大量环境交互，计算成本高
- "游戏状态相似度"是个本质难题

### R3：缺陷到修复的端到端学习

**研究问题**：
> 能否从「游戏运行时的异常行为」直接生成修复代码，而不需要人工定位和分析？

**为什么重要**：
- 我们现在的代码定位是"规则模板+静态扫描"，覆盖面有限（仅 3 类策略）
- 如果能做到端到端的"Bug→Fix"，价值会大很多倍
- 这也是 AI 编程最有挑战的场景之一——不仅要会写代码，还要先理解"什么是错的"

**研究内容**：
1. **数据集构建**：
   - 从开源游戏的 Git 历史中挖掘"缺陷-修复"对
   - 标注缺陷类型、严重程度、修复复杂度
   - 目标：至少 1000 对高质量的游戏 Bug 修复数据
2. **修复模型微调**：
   - 基于通用代码模型（如 CodeLlama、StarCoder）做领域微调
   - 输入：缺陷描述 + 相关代码 + 运行时状态差异
   - 输出：修复 patch
3. **修复验证**：
   - 自动生成的 patch 是否能通过原有测试？
   - 是否引入了新的缺陷（回归测试）？
   - 修复质量的自动评估标准
4. **少样本/零样本修复**：
   - 对于从未见过的缺陷类型，模型能靠常识修复到什么程度？
   - 检索增强（RAG）是否能显著提升修复率？

**里程碑**：
- M1（3月）：完成数据集构建方案，开始数据收集
- M2（6月）：收集 500+ Bug 修复对，训练初版模型
- M3（12月+）：模型迭代 + 论文撰写

**风险与挑战**：
- 高质量游戏 Bug 修复对稀缺——开源游戏本来就少，有详细提交信息的更少
- 游戏代码差异很大（引擎、语言、架构都不同），跨游戏迁移难
- "修复是否正确"的判断本身就是难题

**诚实预期**：
这是难度最高的研究方向，1-2 年内可能做不出可产品化的成果。但哪怕只是把"缺陷定位 Top-K 准确率"从 30% 提升到 60%，也是很大的进步。

### R4：多模态游戏理解

**研究问题**：
> 游戏同时包含视觉表现（画面）、代码逻辑（源码）和运行时状态（内存），如何融合多模态信息做更准确的缺陷检测？

**为什么重要**：
- 我们现在的方案是"多通道独立判定 + 加权汇总"，不是真正的多模态融合
- 不同模态的信息各有盲区：DOM 看不到 Canvas 里的东西，截图读不出精确数值，代码看不到运行时状态
- 如果能真正融合多模态信息，检测准确率会有质的提升

**研究内容**：
1. **各模态的能力边界**：
   - 纯视觉（VLM）能检测到什么类型的缺陷？检测不到什么？
   - 纯代码静态分析能发现什么？漏检什么？
   - 运行时状态（SDK模式）能发现什么？局限是什么？
   - 系统的消融实验，量化各模态的贡献
2. **多模态融合架构**：
   - 早期融合 vs 晚期融合 vs 混合融合
   - 跨模态注意力机制
   - 模态缺失时的降级策略（比如没有 SDK 状态时怎么办）
3. **「画面→状态」逆映射**：
   - 能否从游戏画面反推出内部状态的近似值？
   - 如果能做到，盲测模式的精度会大幅提升
4. **多模态缺陷表示**：
   - 如何用统一的向量空间表示缺陷？
   - 相似缺陷的聚类与检索

**里程碑**：
- M1（2月）：完成各模态能力边界的消融实验
- M2（5月）：实现 2-3 种融合架构，比较效果
- M3（8-12月）：深入研究「画面→状态」逆映射

**风险与挑战**：
- 多模态模型训练成本高
- 游戏类型差异大，通用融合模型可能不存在
- 「画面→状态」逆映射在复杂游戏上可能根本做不到

### R5：AI 测试的可信度度量

**研究问题**：
> 当 AI 说"这里有个 Bug"时，我们能有多信？如何量化 AI 测试结果的可信度？

**为什么重要**：
- AI 测试最大的障碍不是技术，而是信任——研发不信 AI 找的 Bug
- 我们现在有证据强度分级，但那是人工定义的规则，没有经过概率校准
- 如果能给出经过校准的"这个报告是误报的概率是 X%"，用户就知道该花多少精力去验证

**研究内容**：
1. **置信度校准**：
   - AI 给出的"置信度"和"实际正确率"是否匹配？
   - 如何校准？（Platt scaling、Isotonic regression 等）
   - 不同缺陷类型的校准曲线是否不同？
2. **证据融合的数学基础**：
   - 多个证据源独立吗？如果不独立，如何处理？
   - Dempster-Shafer 证据理论是否适用？
   - 贝叶斯更新框架能否用来累计证据？
3. **可信度的组成分解**：
   - 感知可信度（看对了吗？）
   - 推理可信度（想对了吗？）
   - 断言可信度（判对了吗？）
   - 各成分如何分别度量？如何合成？
4. **不确定情况下的决策**：
   - 可信度低于阈值时，应该请人工复核，还是再跑一轮验证？
   - 如何优化"AI 自动判 + 人工抽样复核"的比例？

**里程碑**：
- M1（1月）：收集置信度校准数据，建立基线
- M2（3月）：实现校准方法，验证效果
- M3（4-6月）：完善可信度框架，发布技术报告

**风险与挑战**：
- 需要大量标注数据（真 Bug / 假 Bug 的标注）
- 校准结果可能过拟合特定游戏/缺陷类型
- 纯理论工作容易变成"自说自话"，需要与真实用户场景结合

### R6：开放科学与社区建设

**研究问题**：
> 如何建立一个开放、协作的 AI 游戏测试研究社区？

**为什么重要**：
- 一个人/一个团队的力量有限，社区的力量是无穷的
- PlayRanger 如果能成为社区中心项目，价值远超一个工具本身
- 开放科学也会倒逼我们提高研究质量——所有数据和方法都公开，经得起检验

**具体计划**：
1. **开源游戏缺陷库**：
   - 收集和整理真实游戏的 Bug 及其修复
   - 统一格式标注（缺陷类型、严重程度、复现步骤、修复 patch）
   - 开放给所有研究者使用
2. **年度基准挑战赛**：
   - 基于 GT-Bench（R1），每年办一次挑战赛
   - 邀请学术界和工业界的团队参加
   - 发布年度白皮书，总结进展和趋势
3. **开放研究笔记**：
   - 我们的研究过程、中间结果、失败尝试全部公开
   - 不是等做完了再发论文，而是边做边记
   - 接受社区的质疑和建议
4. **教育资源**：
   - 「AI 游戏测试入门」教程
   - 经典论文导读
   - 实验复现指南

**里程碑**：
- 持续进行，与 R1-R5 同步推进
- 每季度更新一次开放数据集
- 每年发布一份「AI 游戏测试现状」白皮书

## 四、研究优先级排序

按「短期可落地 + 长期价值」二维排序：

```
              高长期价值
                  │
         R3       │       R2
   缺陷修复端到端  │  高效探索策略
                  │
 ─────────────────┼───────────────── 高短期价值
                  │
         R6       │       R1
   开放科学社区   │   基准测试套件
                  │
         R4       │       R5
   多模态融合     │   可信度度量
                  │
              低长期价值
```

**推荐执行顺序**：
1. **先做 R1（基准测试）**：既是研究基础设施，又是产品测试工具，投入产出比最高
2. **同步做 R5（可信度度量）**：难度中等，3-6 个月可见效，直接提升产品说服力
3. **然后 R2（高效探索）**：难，但价值大，作为长期主攻方向
4. **同时推进 R6（社区建设）**：持续投入、细水长流
5. **条件成熟再做 R4（多模态）和 R3（端到端修复）**：需要更多资源和积累

## 五、研究方法与质量保证

### 5.1 反证原则

每个研究假设都必须：
1. 先想"怎么证明我是错的"，再想"怎么证明我是对的"
2. 设计对照组实验，而不是只看自己的方法有多好
3. 报告负面结果——失败的尝试和成功的尝试同样有价值

### 5.2 数据真实性

- 所有实验数据必须可复现
- 代码和数据全部开源（除非有隐私/版权限制）
- 不挑数据、不删异常值，除非有充分理由
- 统计显著性检验：p < 0.05 才算显著，效应量也要报告

### 5.3 多方验证

重要结论至少要通过两种独立方法验证：
- 模拟实验 + 真实游戏测试
- 自动评估 + 人工评估
- 不同游戏/不同缺陷类型上的一致性

### 5.4 诚实标注

论文/报告中必须明确：
- 哪些是实验结果，哪些是推测
- 数据来源和局限性
- 可能的偏差来源
- 适用范围和不适用场景

## 七、成功指标

**不是看发了多少论文，而是看：**

1. **基准被用了吗？**：有多少外部团队用 GT-Bench 评估他们的 Agent？
2. **方法被引用了吗？**：研究成果被其他研究者引用了多少次？
3. **产品用上了吗？**：研究成果转化到 PlayRanger 产品中的比例是多少？
4. **社区活跃吗？**：有多少外部贡献者？讨论质量如何？
5. **我们错了多少次？**：有多少假设被实验推翻了？（这不是失败，是科学方法的正常过程）
