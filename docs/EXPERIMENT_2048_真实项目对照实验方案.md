# PlayRanger 2048 真实项目对照实验方案（量化效率提升）

> 对象：真实第三方开源游戏 **2048**（MIT，`gabrielecirulli/2048`，commit `478b6ec346e3787f589e4af751378d06ded4cbbc`）
> 目的：在「非自研、无 SDK、源码未改」的真实项目上，量化 PlayRanger 相对人工测试的发现、定位与修复效率。
> 关系：本方案是 [`EXPERIMENT_真实项目对照实验方案.md`](EXPERIMENT_真实项目对照实验方案.md) 的 2048 专项实例；通用方案定义口径，本方案给出可直接执行的缺陷清单、分组与时序。

---

## 一、实验定位与边界

### 1.1 为什么用 2048 做对照

| 理由 | 说明 |
|---|---|
| 真实第三方 | 上游公开仓库，不是为 PlayRanger 写的演示游戏 |
| 源码未改 | 14 个文件登记 SHA-256，`PROVENANCE.json` 可逐文件复核；测试断言目录无夹带代码 |
| 结构不同 | 10 个 JS 文件分层，原型式 `GameManager.prototype.setup = function`、`var self = this`、渲染与状态分离 |
| 无 SDK | 不能靠游戏上报状态，必须走「盲测 DOM / 只读探针」路线，正好对应第三方游戏的真实处境 |
| 可注入、可重置 | 纯前端 + `localStorage`，复制目录即可造缺陷变体；清 `gameState / bestScore` 即可重置 |

### 1.2 本实验能证明 / 不能证明

**能证明**：在 2048 这一被试上、本次模型版本下，三组（人工 / 盲测 / 状态桥接）的缺陷发现率、误报率、证据完整率、单缺陷耗时差异；以及「从缺陷包到源码行 + patch」的工具/人工耗时差异。

**不能证明**：不能外推到所有 Web 游戏，不能外推到 Unity / 原生手游，不能证明「AI 一定比人强」。样本量按小样本处理，只报区间、配对差值与相对变化，不硬套 p 值。

### 1.3 与已完成验证的区分

| 已完成（静态级） | 本实验（运行时级） |
|---|---|
| 原生源码 4/4 字段归属正确 | 10 个缺陷能否被**自动发现** |
| 注入副本 3/3 patch 正确（静态测试删掉了 `setup` 内两处 `score` 写点） | 发现的**误报率、复现率、耗时** |
| 单次定位中位 139 ms | 与**人工定位**的对照 |
| 16 项测试 / 236 项回归通过 | 三组 × 3 轮的完整对照数据 |

> 静态验证证明「指得准」，本实验证明「找得到、找得快、值得用」。两者不可互相替代。
>
> 两处口径必须分清：静态测试的「遗漏重置」样本是把 `setup` 里**两处** `this.score` 写点都删掉，策略才会触发；本实验 D01 只让「新局」分支失效（`this.score = this.score || 0;`），字段写点仍在，因此预注册 patch **不可用**——这不是矛盾，而是「字段是否还被写入」这个前提条件不同。

## 二、待验证假设与判定线（预注册）

| 编号 | 假设 | 判定线（达到即支持） |
|---|---|---|
| H1 | 状态桥接组的发现率不低于人工组 | C 组发现率 ≥ A 组 − 5 个百分点 |
| H2 | 工具组的证据完整度显著高于人工 | C 组证据三要素完整率 ≥ 90%，A 组 ≤ 50% |
| H3 | 工具组单缺陷耗时低于人工 | C 组单缺陷耗时 ≤ A 组的 70%（下降 ≥ 30%） |
| H4 | 误报率可接受 | B / C 组误报率 ≤ 20% |
| H5 | 缺陷可稳定复现 | 抽样回放复现率 ≥ 80% |
| H6 | 代码级定位显著快于人工定位 | D 组中位耗时 ≤ E 组的 30%；「可操作定位率」≥ 60%（本电池预注册 6/10）。Top-1 单列报告，不设及格线（预注册预期偏低，见 4.1） |
| H7 | 接入成本足够低 | 从零到首份 2048 报告 < 0.5 人日 |

反假设（必须一并报告）：
- 若 H3 不成立，检查是否因 A 组可用 DevTools 直接读 `localStorage`，导致人工基线偏高；
- 若 H4 超阈，给出误报的异常类型分布，并说明是 VLM 误判、状态探针缺失还是缺陷判定口径问题；
- 若 H6 不成立，区分是「定位错」还是「patch 不可用」——两者不是一回事；
- 若 H6 的耗时成立但 Top-1 偏低，说明工具价值在「快速缩小范围 + 给出可应用 patch」，而不是「第一条必须排对」；报告中必须同时给出 Top-1 与可操作定位率，不允许只报好听的那个。

## 三、被试材料与冻结

### 3.1 基线版本

| 项 | 值 |
|---|---|
| 上游 | `https://github.com/gabrielecirulli/2048` |
| commit | `478b6ec346e3787f589e4af751378d06ded4cbbc`（2024-10-24） |
| 许可 | MIT |
| 本地夹具 | `tests/fixtures/thirdparty_2048/`（14 个文件） |
| 完整性 | `PROVENANCE.json` 登记逐文件 SHA-256；`tests/test_p3_1_thirdparty_game.py::TestUpstreamIntegrity` 校验 |
| 缺失资源 | 字体、favicon、apple-touch 图标未纳入；不影响玩法，仅记录 404，不作为缺陷 |

### 3.2 运行环境

- 浏览器：本机 Edge（`C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`），版本写入实验报告；
- 启动：在夹具目录起静态服务（如 `python -m http.server 8765`），Playwright 通过 `PLAYWRIGHT_CHROMIUM_PATH` 指向 Edge；
- 视口：固定 `1280×800`，缩放 100%；
- 模型：固定模型名、版本与温度（写入报告）；VLM 调用次数单独计费。

### 3.3 确定性夹具（实验侧，不改源码）

2048 直接调用 `Math.random()`，且没有 SDK。为让三组可比，实验统一注入**种子垫片**；**状态探针只给 C 组**（B 组必须保持盲测；A 组不挂探针，但允许用 DevTools 自行读取 `localStorage`）。两个脚本都通过 `page.addInitScript` 注入，不修改上游文件：

1. **种子垫片（三组统一）**：读取 `window.__PLAYRANGER_SEED__`，用 mulberry32 覆写 `Math.random`。每轮固定种子，保证新 tile 的位置与数值序列可复现。
2. **状态探针（仅 C 组）**：hook `Storage.prototype.setItem`，把最近一次 `gameState` 写入 `window.__PR_LAST_STATE__`；同时暴露只读函数 `window.__PR_STATE__()`，返回 `score / over / won / bestScore / grid / DOM 分数 / 结束提示`。
   - 只观察，不写入游戏状态；
   - 即使 `game over` 后游戏清空 `gameState`，探针仍保留最后一次快照。

> 注意：种子垫片与状态探针是**实验夹具**，不是产品能力。产品当前只注入全局变量 `__PLAYRANGER_SEED__`，不会自动覆写 `Math.random`；这一点已如实写入提交文档的「不足」。

### 3.4 固定局面夹具（仅 D05 / D06 使用）

通过 `localStorage.gameState` 预置合法棋盘（不改源码），用于可控触发：

```json
{
  "grid": {
    "size": 4,
    "cells": [
      [{"position": {"x": 0, "y": 0}, "value": 1024}, null, null, null],
      [{"position": {"x": 1, "y": 0}, "value": 1024}, null, null, null],
      [null, null, null, null],
      [null, null, null, null]
    ]
  },
  "score": 0, "over": false, "won": false, "keepPlaying": false
}
```

- D05：预置「同一行两个 1024」的棋盘，按左键合并即达 2048；
- D06：预置满盘且存在可合并对的棋盘；由于合并后会补一个随机 tile，需用固定种子预演并挑选「补位后仍存在可合并对」的局面，把该局面与种子一并写入夹具。

预置数据与预期结果一并写入 `defect_manifest.json`，供仲裁者复核。

### 4.1 预注册的定位预期（防止事后挑好听的说）

| ID | 预期定位结果 | 预期 patch 是否可用 | 理由 |
|---|---|---|---|
| D01 | 能进 Top-3（`setup:42/:48` 均为 `this.score` 写点）；Top-1 落在 `:42`，距注入行 `:48` 六行，按「同函数 ±3 行」判 Top-1 不中 | **否** | 注入后 `setup` 仍有 `this.score` 写点；「遗漏重置」策略要求重置函数内查不到该字段写点 |
| D02 | 能进 Top-3（`move:167`）；Top-1 被 `setup:42/:48` 抢占 | 否 | 写点能定位，但不属于三类渲染/重置策略 |
| D03 | 仅 patch 指向正确行：`html_actuator.js:112`；Top-3 被 4 个 1.0 写点挤出 | 能（渲染偏移） | `textContent = this.score - 100` 可识别并还原 |
| D04 | 同上 | 能（渲染未绑定） | 字面量 `"0"` 可识别并还原 |
| D05 | 能进 Top-3（`move:170`，`self.won` 写点与注入行同线） | 否 | 缺陷在判定条件，不是字段写点缺失 |
| D06 | 能进 Top-3（`move:186` 的 `this.over` 写点，距注入行 1 行） | 否 | 条件表达式缺陷 |
| D07 | **否** | 否 | 重复事件注册无法靠字段扫描发现 |
| D08 | **仅候选**：`serialize:105` 以 declaration 命中，但排在 4 个写点之后（约第 5 位），不进 Top-3 | 否 | 对象字面量赋值，不是 `this.score = ...` |
| D09 | **否** | 否 | 输入节流逻辑，非状态字段 |
| D10 | **仅候选**：`actuate:80` 的 `this.score` 以 read 命中，排在写点之后 | 否 | 方法返回值比较，不是字段写点 |

> 预注册预期：**可操作定位 6/10**（Top-3 直接命中 4/10：D01 / D02 / D05 / D06；仅 patch 指向正确行 2/10：D03 / D04），**patch 可用 2/10**，**预期失败 4/10**（D07–D10）。实测若偏离，同时报告「预注册值 / 实测值 / 偏离原因」，不得删样本。

**静态复核（2026-11-16，注入副本实跑当前 `locate_bug`）**：D01 / D02 的 patch 为空，Top-3 分别含 `setup:42/:48` 与 `move:167`；D03 / D04 的 patch 精确改回 `html_actuator.js:112`；D08 patch 为空，`serialize:105` 仅以 declaration 命中。与上表一致。

由此确认一条**排序局限**：写点权重 1.0 会排在对象字面量（declaration 0.8）和渲染读点（read 0.5）之前，在多写点文件里 Top-1 容易落到 `setup` 的首个赋值。该局限已作为提交文档「不足 4」的实测依据；本实验**不据此调整权重**——否则就是在测试集上调参，后续只能用新缺陷集验证改进。

## 五、实验分组

| 组 | 角色 | 可用信息 | 投入上限 | 产出 |
|---|---|---|---|---|
| A 人工探索 | 2 名测试者（T1 玩过 2048 ≥10 局；T2 未玩过） | 浏览器 + DevTools；**不看源码**；不知道埋点 | 每人 60 min | Bug 单（描述 + 触发步骤 + 截图/录屏 + 时间戳） |
| B 盲测 | PlayRanger，DOM + 截图 + VLM | 无源码、无状态探针 | 机时 60 min + 人工复核 20 min | 缺陷包 + 报告 |
| C 状态桥接 | PlayRanger + 只读探针 + 种子垫片 + 代码定位 | 有源码（定位阶段） | 机时 60 min + 复核 20 min | 缺陷包 + 报告 + `file:line` + patch 草案 |
| D 工具定位 | PlayRanger `locate` + `advise` | 给定 10 个缺陷包 + 源码 | 每缺陷 ≤5 min | Top-1 / Top-3 / 可操作 / patch / 置信度 / 耗时 |
| E 人工定位 | 1–2 名开发 | 缺陷包 + 源码 + DevTools | 每缺陷 ≤10 min（超时记 10 min） | 首个正确 `file:line` + patch + 耗时 |

说明：
- 本方案的 **C 组是「状态桥接」**，与通用方案中可选的「C 协同组」不是同一概念；
- A 组允许 DevTools 读 `localStorage`，这是真实测试者的正常手段；因此 A 在状态类缺陷上并不弱，基线更可信。
- B / C 组不给埋点清单，只给同一句目标：「尽可能发现可复现的异常，并写明触发步骤」。
- D / E 组与发现实验解耦，用同一批预注册缺陷包，专门测「定位效率」，避免把「找得到」与「定位快」混在一起。

### 5.1 轮次与顺序

- 每轮 = 10 个 build 全测一遍；共 3 轮；
- 每轮开始前：清空 `localStorage.gameState / bestScore`，重置种子，清空 PlayRanger 记忆与缺陷目录；
- build 顺序每轮随机；A / B / C 的执行顺序在轮次间交替（缓解学习效应）；
- 第 1 轮为主分析，2–3 轮作重复性检验；学习效应单独报告（第 2/3 轮相对第 1 轮的变化）。

### 5.2 仲裁

- 2 名未参与测试的评审独立判定每条报告是否「真实、可复现、非重复、对得上某个埋点」；
- 一致性要求 Cohen's Kappa ≥ 0.6；低于则重定义判定口径后重评；
- 判定按「行为一致」而非「措辞一致」。

## 六、指标定义与公式

| 指标 | 公式 | 备注 |
|---|---|---|
| 发现率 | 命中埋点数 ÷ 10 | 每轮每组各算一次 |
| 严重度加权发现率 | Σ(权重 × 命中) ÷ Σ(权重 × 全部埋点)，blocker=5 / critical=4 / major=3 / minor=2 / info=1 | 防止只抓小问题 |
| 误报率 | 仲裁无效报告数 ÷ 报告总数 | 无效含：不存在、不可复现、重复、把设计当缺陷 |
| 证据完整率 | 具备「截图 + 触发步 + 字段级差异」的缺陷数 ÷ 有效缺陷数 | 人工通常只有文字 |
| 复现率 | 回放 3 次中 ≥2 次 `reproduced` 的缺陷数 ÷ 抽样 5 条 | 三态：reproduced / partial / not_reproduced |
| 定位 Top-1 准确率 | 「命中注入点所在函数且行号 ±3」的缺陷数 ÷ 10 | ±3 容忍同函数内相邻语句 |
| 定位 Top-3 召回 | 正确位置出现在前 3 条命中里的缺陷数 ÷ 10 | 衡量候选排序 |
| 可操作定位率 | （Top-3 命中 或 patch 精确指向注入行）的缺陷数 ÷ 10 | 本电池预注册 6/10；回答「拿到的东西能不能直接动手」 |
| patch 可应用率 | `git apply --check` 通过的 patch 数 ÷ 10 | 只算工具组 |
| patch 正确率 | 应用后「目标缺陷消失 + 其余 9 个埋点行为不变 + 冒烟清单通过」的缺陷数 ÷ 10 | 需人工执行验证清单 |
| 单缺陷耗时 | (人时 + 机时 × 折算系数) ÷ 有效缺陷数 | 折算系数默认 1.0，报告首页声明 |
| 定位耗时 | 从拿到缺陷包到写出首个正确 `file:line` 的秒数 | D / E 组逐条记 |
| MTTR（模拟） | 定位耗时 + patch 应用 + 验证清单执行 | 只对 patch 可应用的缺陷算 |
| API 成本 | 步数 × 单步 token 成本 + VLM 次数 × 单次成本 | 附账单截图 |
| 回收点 | 工具接入成本 ÷ 单缺陷节省工时 | 回答「跑多少次回本」 |

> 成本口径必须在报告首页写清：人时是否含准备、机时如何折算、API 是否含重跑。

## 七、执行 SOP

### 阶段 0：准备（约 4 小时）

1. 按第 3.1 节冻结 2048 版本，复制 10 份 `builds/Bxx`，逐份注入第 4 节缺陷；
2. 每份 build 由第三人按触发路径手工复现一次，确认「缺陷可见」，不可触发则修正注入后重来；
3. 生成 `defect_manifest.json`（ID、文件:行、触发路径、期望/实际、真值严重度、预注册定位预期）；
4. 固定浏览器、视口、模型版本与温度、种子；
5. 培训 2 名仲裁者：用 3 条示例各判一次，对齐口径；
6. 对种子垫片做一致性自检：同一种子连续启动 3 次，前 10 个 tile 序列应一致。

### 阶段 1：单轮执行（约 4 小时）

```
T+0     清空 gameState / bestScore / 记忆 / 缺陷目录；重置种子
T+0     启动 A 组（2 人并行，各 60 min，全程录屏）
T+0     启动 B / C 组（后台跑，目标与 A 一致；C 组挂只读探针）
```

## 九、统计口径与报告纪律

1. **主报告**：给「3 轮均值 + 最小值~最大值区间」，不报单点结论；
2. **配对比较**：同一轮、同一缺陷内比较 A/B/C 与 D/E，报告逐条差值与相对变化；
3. **效应量**：用相对变化（如「单缺陷耗时下降 X%」）；样本允许时附 Wilcoxon 符号秩检验作为补充，并注明样本量与轮次相关性局限；
4. **必须报告反例**：D07–D10 是预注册的「工具预期失败样本」，必须原样报告；若工具意外命中，也要说明是否属于误打误撞；
5. **不得外推**：结论限定「2048 + 本次 10 个注入缺陷 + 本次模型版本 + Web 浏览器」；
6. **先写不能证明什么**：报告首页先列边界，再列结论。

## 十、风险与偏差控制

| 风险 | 影响 | 控制手段 |
|---|---|---|
| 2048 随机性强 | 同一操作序列结果不同 | 种子垫片 + 每轮固定种子；启动一致性自检 |
| 人工可用 DevTools | A 组基线偏高 | 这是真实手段，不限制；报告中说明，避免把 A 说成「不会用工具」 |
| 测试者玩过 2048 | 发现率虚高 | T1/T2 分层报告；至少保留 1 名未玩过的测试者 |
| build 编号泄漏 | 测试者按编号猜缺陷 | build 随机编号；manifest 不对测试者可见；每轮重排 |
| 动画/渲染时序 | 复现率偏低 | 沿用 PlayRanger 的稳定等待；回放三次取三态，不强行判成功 |
| VLM 抖动 | B 组结果不稳定 | 固定模型版本与温度；同轮重跑一次取并集，并在报告中声明 |
| `game over` 清空存档 | 状态探针读不到 | hook `Storage.setItem` 保留最后快照 |
| patch 上下文冲突 | 可应用率虚低 | 每个 build 是独立副本；patch 路径固定 `a/js/...` |
| 缺失图标/字体 404 | 被误报成缺陷 | 阶段 0 记录 404 清单，仲裁时排除 |
| 学习效应 | 后两轮偏容易 | 轮次间换 build 顺序与组顺序；第 1 轮为主分析 |
