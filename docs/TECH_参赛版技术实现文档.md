## 一、应用价值（30% 权重）

### 1.1 我们解决什么问题

独立游戏开发者和小团队面临的 QA 困境：

- **人手不够**：3-5 人的团队，每个人身兼数职，没有专职测试
- **没有测试脚本**：写自动化测试需要学习框架、维护用例，成本比收益大
- **Bug 上线后才发现**：靠人工点测覆盖不全，玩家反馈的 Bug 往往比内部测试多
- **不知道 Bug 怎么复现**：玩家报告"卡住了""闪退了"，但没有复现步骤，研发无从下手
- **修复了不敢上线**：怕修一个 Bug 引出新 Bug，没有回归测试保障

PlayRanger 用 AI Agent 代替人工做重复性的试玩测试，让小团队也能拥有"7×24 小时不停玩"的测试员。

### 1.2 目标用户与使用场景

| 用户角色 | 典型场景 | 核心价值 |
|---|---|---|
| **独立游戏开发者**（1-3人） | 每次提交后跑一遍基础回归，别把老 Bug 带回来 | 零脚本、五分钟上手、自动出报告 |
| **中型独立工作室**（5-20人） | 上线前密集测试，多台机器并行跑，找边角 Bug | 并发调度、缺陷归档、修复验证、团队协作 |
| **技术美术 / 策划** | 改了数值/布局/美术资源，确认没把玩法搞坏 | 不用懂代码，URL 丢进去就能测 |
| **发行/QA 外包** | 一次性测多款游戏，快速出评估报告 | 批量任务、统一格式、可审计证据 |

### 1.3 为什么"现在"做这个

1. **LLM 能力跨过了临界点**：2024 年之前的模型还做不好"理解游戏画面+做动作决策+判断对错"的闭环，2025-2026 年的多模态模型已经可以了。
2. **独立游戏市场持续增长**：Steam 每年新增上万款独立游戏，但这些团队的测试能力没有同步提升。
3. **AI 测试是增量市场**：全球游戏 QA 市场约 60 亿美元/年（Global Info Research, 2025），AI 赋能的测试是增长最快的细分。

> **数据来源说明**：市场规模数据来自公开行业报告，不同报告统计口径不同（QA 服务 vs 自动化工具 vs 试玩模拟），以上仅作为方向判断，不作为精确数字引用。

### 1.4 诚实标注：哪些场景我们不适用

- **3A 级大型游戏**：我们目前只支持 Web 游戏/HTML5 游戏
- **强依赖手感的动作游戏**：帧率精确判定、操作延迟这类指标需要引擎内 SDK，纯盲测做不到
- **完全依赖视觉判断的游戏**（纯 Canvas/WebGL 且无 DOM 状态）：盲测模式只能靠截图+VLM，成本高且精度有限
- **需要法律级证据的场景**：我们的证据链是工程级的，不是司法鉴定级的

### 1.5 量化验证：2048 C 组实测数据

为了避免"AI 测试就是个 demo"的质疑，我们在真实第三方开源游戏 **2048**（MIT，未修改源码）上做了 C 组「状态桥接」对照实验：用 Playwright 浏览器 + 只读状态探针 + 代码定位，验证 5 个预注册缺陷的可发现性与可定位性。

**实验设计**：
- 5 个预注册缺陷，覆盖 状态类 / UI 类、major / critical 严重度
- 固定种子 + 预置棋盘 + 针对性动作序列，确保结果可复现
- 状态探针 + DOM 双重验证发现，代码定位用纯静态扫描（不依赖 LLM）

**结果（C 组，5 缺陷 × 确定性触发）**：

| 指标 | 值 | 说明 |
|---|---|---|
| 缺陷发现率 | **100%**（5/5） | 5 个预注册缺陷全部被发现 |
| Top-3 定位召回 | **80%**（4/5） | 正确位置出现在 Top-3 候选中 |
| 可操作定位率 | **100%**（5/5） | Top-3 命中 或 patch 精确指向注入行 |
| patch 可应用率 | **20%**（1/5） | 渲染偏移类缺陷可直接 patch，状态类需人工确认 |
| 定位中位耗时 | **~149 ms** | 纯静态扫描，单文件毫秒级 |

**逐条对照**：

| ID | 缺陷 | 类别 | 严重度 | 发现 | Top-3 | patch可用 | 定位耗时 |
|---|---|---|---|---|---|---|---|
| C01 | 重开后分数未归零 | 状态 | major | ✅ | ✅ | ❌ | 158 ms |
| C02 | 合并计分少加 | 状态 | major | ✅ | ✅ | ❌ | 170 ms |
| C03 | DOM 分数比真实值少 100 | UI | major | ✅ | ❌ | ✅ | 149 ms |
| C05 | 合成 2048 不触发胜利 | 状态 | critical | ✅ | ✅ | ❌ | 146 ms |
| C06 | 满盘仍可合并却 Game Over | 状态 | critical | ✅ | ✅ | ❌ | 40 ms |

> **诚实说明**：
> 1. 种子垫片与状态探针是**实验夹具**（保证确定性和状态可读），不是产品能力。盲测模式（B 组）下发现率会低于此数据。
> 2. 代码定位目前覆盖 3 类简单模式（遗漏重置 / 渲染偏移 / 渲染未绑定），状态类条件缺陷只能定位到写点附近，不能精确到条件表达式。
> 3. 样本量为 5（C 组），属于小样本验证，不做统计显著性宣称。
> 4. 完整实验脚本与原始数据见 `tools/run_2048_cgroup.py` 和 `output/experiments/2048/c_group_report.json`。

### 1.6 消融实验：零接入纯 DOM 到底能看出多少（B1 组）

C 组用了状态探针（读内部真值），自然会被追问"**不让你读内部状态、只看用户能看到的界面呢？**"。为此补了 B1 消融：同一批 5 个缺陷、同样的确定性触发，唯一变量是**证据通道只保留用户可见 DOM**（`.score-container` / `.game-over` / `.game-won` / 棋子值），并且每个缺陷都与「同种子、同预置、同动作」的**干净源码基线**对照。

| 指标 | 值 | 含义 |
|---|---|---|
| DOM 检出率（带期望值断言） | **5/5（100%）** | 知道正确结果时，分数/胜负都反映在 DOM，可与基线区分 |
| **零 oracle 自明率** | **1/5（20%）** | 不带任何期望值、只看一帧界面就能判定是 Bug 的比例 |

唯一"零期望也能看出"的是 D03：变异把 DOM 分数渲染成 `真实分 − 100`，在 4 分局面下显示 **−96**，负分违背常识。其余 4 个（分少加、重开不归零、该赢没赢、不该结束却结束），单看一帧 DOM 无法判断对错——因为 Agent 并不知道"正确分数应该是多少"。

**这个结论恰好论证了产品的双模式设计**：

- 想要高精度/可复现 → **SDK 精确模式或状态桥接**（有真值，C 组 5/5）；
- 零接入测第三方/已上线游戏 → **盲测模式**，不能只靠单帧 DOM，必须用 LLM/VLM 做语义推理 + 多次复现交叉确认，并把结论降为 `auto_warning`。B1 给出的是该通道的**上限**，不是盲测发现率；真正的零 oracle 盲测数据（B2）仍在待办，我们不拿上限冒充实际效果。

> 脚本与数据：`tools/run_2048_bgroup_dom.py`、`output/experiments/2048/b1_group_report.json`。

## 二、创新性（30% 权重）

### 2.1 三条差异化主轴

我们做了大量竞品调研（GameDriver、AltTester、modl.ai、Applitools、人工外包等），发现了三个竞品结构性空白：

#### 差异化一：证据可审计（Evidence You Can Audit）

**现状**：所有竞品的 Bug 报告——有的给日志（GameDriver）、有的给像素差异（Applitools）、有的给录像（modl.ai）、有的给文字描述（人工测试）——但没有一家提供**标准化的、可交叉验证的证据包**。

当测试是 AI 做的，研发天然不信。"你说有 Bug，我怎么知道不是 AI 看错了？"

**我们的方案**：
- 每个缺陷附带**多通道证据**：SDK 状态快照（如果接了）+ DOM 结构 + 截图 + 操作序列 + 断言触发记录
- **证据强度分级**：单通道发现 → 双通道一致 → 三通道交叉验证 → 人工复核
- **可复现操作序列**：每个 Bug 都有完整的操作步骤记录，按步骤回放一定能复现（如果游戏支持种子，则 100% 确定）

#### 差异化二：结论到修法（From Bug to Fix）

**现状**：所有竞品都止步于"发现+报告"。发现 Bug 之后怎么办？那是研发自己的事。

**我们的方案**：
- **代码定位**：根据缺陷类型（遗漏重置/渲染偏移/渲染未绑定等），自动扫描源码，定位到可能的文件和行
- **修复草案**：针对可识别的缺陷模式，自动生成 patch 草案
- **沙箱验证**：patch 在隔离沙箱中校验（`git apply --check`），可应用到副本，并可选运行测试命令验证
- （P1 计划）**自动回归**：patch 应用后自动重跑原任务，确认缺陷消失且没引入新问题

这不是"AI 自动修 Bug"的噱头——我们不声称能自动修所有 Bug。但哪怕只是把"读报告+搜代码+定位"的时间从 15 分钟压缩到 2 分钟，也是可量化的效率提升。

#### 差异化三：零接入私有化（Zero-Onboarding & Private）

**现状**：几乎所有专业游戏测试工具都要求接入 SDK 或上传到云。对独立开发者来说，接入成本高、有隐私顾虑。

**我们的方案**：
- **盲测模式**：给一个 URL 就能测，游戏侧什么都不用改。用 DOM 解析 + 截图 VLM + 启发式操作做探索
- **SDK 模式（可选）**：如果愿意接几行轻量 SDK，就能拿到真值状态，测试精度大幅提升。两种模式同一套 Agent 逻辑
- **本地运行**：所有数据都在本地，源码不上传、截图不上传、测试报告不上传。断网也能用（如果用本地 LLM）

### 2.2 与现有方案的对比

| 维度 | 人工测试 | GameDriver/AltTester | modl.ai | Applitools | **PlayRanger** |
|---|---|---|---|---|---|
| 需要接 SDK | ❌ 不需要 | ✅ 必须接 | ✅ 必须接 | ❌ 不需要 | **❌ 盲测模式不需要** |
| 能发现玩法 Bug | ✅ 能 | ✅ 能（写脚本） | ✅ 能 | ❌ 只看视觉 | **✅ 能（Agent 自主探索）** |
| 代码级定位 | ❌ 不能 | ❌ 不能 | ❌ 不能 | ❌ 不能 | **✅ 能（静态扫描+模式匹配）** |
| 可复现操作序列 | ❌ 不一定 | ✅ 脚本就是 | ✅ 有 | ❌ 没有 | **✅ 有（步骤完整记录）** |
| 可审计证据 | ❌ 描述主观 | ⚠️ 日志+截图 | ⚠️ 录像 | ✅ 像素级 diff | **✅ 多通道交叉验证** |
| 私有化部署 | N/A | ✅ 企业版 | ❌ 云服务 | ✅ 企业版 | **✅ 完全本地运行** |
| 价格 | 贵（按人天） | 中（按 seat） | 贵（企业定价） | 中（按调用量） | **开源免费 + 可选商业支持** |

### 2.3 创新点总结

1. **双模式设计**：盲测（零接入）+ SDK（高精度），同一 Agent 架构，可平滑升级
2. **证据标准化**：多通道采集 + 强度分级 + 可复现序列，建立 AI 测试的信任基础
3. **缺陷→定位→修复→验证**全链路：从"告诉你有 Bug"到"告诉你在哪、给你 patch 草案、帮你验证"
4. **并发自适应调度**：根据本机内存自动算出最大并行数，单机资源最大化利用
5. **无头模式性能兜底**：rAF 被节流时自动切换 CDP Performance 指标，绝不伪造 FPS

### 3.2 核心技术要点

#### 3.2.1 Agent 架构：ReAct + 工具调用

`ReActLoop` 是 Agent 的核心循环，采用 Reasoning + Acting 模式：

```
观察(observe) → 思考(think) → 决策(decide) → 行动(act) → 观察(observe) → ...
```

Agent 可以调用的工具：
- **探索类**：点击元素、输入文本、按键、滚动、悬停、等待
- **感知类**：获取 DOM 结构、截图、URL、页面标题、运行时状态
- **断言类**：检查元素存在、检查文本、检查数值范围、检查帧率
- **记录类**：截图存档、记录 Bug、上报进度

每一步都有 `on_step` 回调，可以中断（`cancelled` 状态），支持协作式取消。

#### 3.2.2 双模式感知

**盲测模式（零接入）**：
- DOM 解析：用 Playwright 获取页面元素树，提取可交互元素
- 截图+VLM：当 DOM 信息不足时（Canvas 游戏），调用多模态模型理解画面
- 启发式操作：基于"先找可点击元素→试操作→观察变化"的通用策略

**SDK 模式（可选接入）**：
- 游戏侧注入轻量 SDK，暴露 `getState()` 方法
- Agent 可以直接读取游戏内部状态，精度从"像素级"提升到"状态字段级"
- 支持写入 `window.__PLAYRANGER_SEED__` 实现确定性复现

#### 3.2.3 证据链与缺陷判定

每个缺陷包含：
```
defect = {
  id, type, severity, description,
  evidence: {
    dom_snapshot: "...",      // DOM 结构快照
    screenshot: "path.png",    // 截图
    action_sequence: [...],    // 触发操作序列
    assertions_failed: [...],  // 失败的断言
    sdk_state_diff: {...}      // （SDK模式）状态差异
  },
  confidence: 0.0-1.0,         // 置信度
  evidence_strength: "single|dual|triple|human",  // 证据强度
  code_location: {             // （可选）代码定位
    file, line, snippet, patch
  }
}
```

判定逻辑：单通道发现标记为"可疑"，双通道独立发现升级为"确认"，三通道一致+断言命中标记为"高置信"。

#### 3.2.4 并发自适应公式

```python
available_gb = 总内存 - 已用内存
per_worker_mb = 1536 (默认, 可配置)
reserve_gb = 2.0 (系统预留, 可配置)

recommended = floor((available_gb - reserve_gb) * 1024 / per_worker_mb)
recommended = clamp(recommended, 1, min(hard_max, cpu_count))
```

- 可用环境变量覆盖：`PLAYRANGER_PER_WORKER_MB`、`PLAYRANGER_RESERVE_GB`、`PLAYRANGER_MAX_WORKERS`
- 探测方式：psutil 优先，Windows 下 `win32api` 兜底
- 默认 hard_max=8，可放宽至 32

#### 3.2.5 任务状态机

```
queued → running → completed
              ↘   failed
              ↘   cancelled (用户主动停止)
              ↘   interrupted (进程崩溃后恢复标记)
```

- 入队使用条件更新 `status NOT IN ('queued','running')`，避免与调度器竞争
- 启动时扫描遗留的 running 任务，标记为 interrupted
- 每个状态变更都有事件记录

#### 3.2.6 修复沙箱安全机制

```
patch 输入 → 路径校验(无..无盘符相对路径)
        → 白名单校验(必须在 PLAYRANGER_WORKSPACE_ROOTS 内)
        → git apply --check (在临时 git 仓库中)
        → 副本应用 (output/fix_sandbox/<uuid>/)
        → 可选：运行测试命令 (超时可配 5-600s)
        → 结果：可应用 / 冲突 / 测试通过 / 测试失败
```

- 副本上限：20,000 文件 / 800MB
- 忽略目录：`.git`、`node_modules`、`__pycache__`、`output`、`venv` 等
- 沙箱目录互不干扰，原始项目文件只读

#### 3.2.7 无头模式性能兜底

**问题**：无头浏览器中 `requestAnimationFrame` 被节流，导致基于 rAF 的性能采样帧太少、结果不准。

**方案**：当帧样本不足时，自动切换到 CDP `Performance.getMetrics`：
- 切换条件：采样周期内有效帧数 < 阈值
- CDP 指标：`busy_ratio`、`script_ratio`、`layout_ratio`、`heap_used_mb`
- 标记字段：`mode="cdp_fallback"`、`fps_unavailable=true`
- **原则：绝不伪造 FPS**

#### 3.2.8 安全与鉴权

- **密码存储**：PBKDF2-HMAC-SHA256，200,000 次迭代，每个用户独立 16 字节随机盐
- **Token 机制**：32 字节 urlsafe 随机数，服务端存储（SHA-256 哈希），有效期 7 天
- **首用户管理员**：第一个注册的用户自动获得 admin 角色（事务内判断）
- **API 鉴权**：`Authorization: Bearer <token>` 头部，校验失败返回 401
- **前端存储**：Token 存 `localStorage`，401 自动清除并跳转登录页

### 4.2 交互设计原则

1. **一屏掌控**：系统状态、并发控制、任务列表、详情查看，都在一个屏幕内完成，不需要多层跳转
2. **实时反馈**：任务进度、事件流每 1.6 秒轮询更新，接近实时感
3. **渐进式信息**：列表只显示关键信息（状态、进度、Bug 数），点进去再看细节（步骤时间线、截图、证据）
4. **诚实状态**：失败就是失败，不确定就是"可疑"，不用绿色图标掩盖问题
5. **可操作的错误**：每个失败状态都有"重跑""查看日志""复制错误信息"等下一步动作

### 4.3 设计风格

- **深色主题**：工程/控制台风格，长时间使用不刺眼
- **等宽字体**用于数据和代码，比例字体用于描述
- **状态色严格规范**：绿色=正常/成功、黄色=警告/排队、红色=错误/失败、蓝色=信息/运行中、紫色=特殊/管理员
- **零外部依赖**：纯 HTML/CSS/JS，加载快、离线可用、无隐私泄露

> **自评**：当前 UI 偏工程化，视觉设计是短板。P0 计划重做视觉，增加数据可视化图表和更精致的动效。

## 六、已知不足与下一步

完整不足清单见 `SUBMISSION_功能说明与亮点不足.md` 和 `ROADMAP_不足收敛与差异化.md`。

最高优先级的 3 个不足：

1. **盲测模式（B 组）发现率未量化**：C 组状态桥接 5/5 全发现，但盲测模式（纯 DOM + 截图 VLM）的数据尚未补齐，实际使用中盲测精度会低于状态桥接。

3. **代码定位覆盖面有限**：只能处理 3 类简单模式，跨文件调用链级别的定位做不了。
