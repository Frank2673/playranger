# PlayRanger「试玩队」— 5 分钟 Demo 录屏分镜脚本（OBS）

> 目标：一条 5 分钟左右的录屏，讲清楚「AI Agent 自动试玩 → 发现缺陷 → 给证据 → 定位代码 → 可验证」，并展示真实实验数据。
> 原则：**只录真实能跑出来的东西**。预置数据是平台真实落盘的数据形态，实验是可现场复跑的，不做无法复现的口头承诺。

---

## 〇、录制前准备（不录，先弄好）

### 1. 启动演示控制台

在项目根目录 `E:\AI造游戏大赛\playranger` 打开 PowerShell：

```powershell
C:\Users\hr173\miniforge3\python.exe tools\demo_server.py
```

- 首次会自动播种演示数据（8 个历史任务 / 8 个缺陷），然后启动服务；
- 看到 `控制台 : http://127.0.0.1:8000/app/` 即成功；
- 想重置数据：`... tools\demo_server.py --seed`。

### 2. 浏览器准备

- Edge / Chrome 打开 `http://127.0.0.1:8000/app/`；
- 窗口最大化，缩放设为 **100%**（Ctrl+0）；
- 先别登录，停在登录页（录制时再登录）；
- 关闭其它无关标签、系统通知、企业微信/QQ 弹窗，任务栏只留演示窗口。

### 3. OBS 设置

| 项 | 建议值 |
|---|---|
| 视频 | 1920×1080，30fps（笔记本屏小就「显示器采集」+ 录制后裁剪，或用「窗口采集」只采浏览器） |

| 水印 | 可不加；加的话右下角小字「PlayRanger · 参赛 Demo」 |
| 备份 | 关键段落（实验复跑）单独再存一份，方便后期 |

> 旁白可以「现场念」，也可以「先录静音操作、后期配音」。下面的【旁白】两种方式都能用。

## 一、分镜表

### 镜头 1 · 开场定调（0:00–0:25，25s）

**画面**：登录页。停顿 2 秒 → 输入 `demo` / `demo1234` → 点登录，进入仪表盘。

**操作要点**：登录后别急着动鼠标，让仪表盘图表有 1–2 秒加载。

【旁白】
> 「独立游戏团队通常没有专职测试，Bug 全靠自己点。PlayRanger 是一个 AI 原生的游戏自动化试玩 Agent：丢给它一个游戏地址，它会像真人一样去玩、去试，并在发现异常时给出可审计的证据，甚至定位到代码。这是它的控制台。」

---

### 镜头 2 · 仪表盘总览（0:25–1:15，50s）

**画面**：仪表盘页。鼠标依次缓慢划过/点到：

1. 顶部 4 个 KPI 卡片（总任务 8 / 累计缺陷 8 / 并发 Worker / 平均完成 16.8s）；
2. 任务趋势图（说一句"这是实时快照"）；
3. 缺陷分布图；
4. 最近任务列表。

**操作要点**：鼠标停在卡片上展示悬浮效果；不要滚动太快。

【旁白】
> 「仪表盘汇总了所有试玩任务。这里有 8 个历史任务，累计发现 8 个缺陷，平均每个任务十几秒跑完。下面是任务状态趋势和缺陷的类型分布，最下面是最近的任务记录。这些数据都来自平台真实落盘，不是写死的页面——每个任务都能点进去看完整过程。」

> 诚实提示：缺陷分布图当前是按总数的经验占比聚合，旁白别说成"精确分类统计"。

---

### 镜头 3 · 任务列表 + 任务详情（1:15–2:30，75s）

**画面**：切到「任务」Tab。

1. 左栏任务列表：展示 completed / failed / interrupted 不同状态标签；
2. 点 `demo-a1f0c9`「DemoGame 全量回归」（42 步、3 缺陷那条）；
3. 右栏出现任务详情：进度条、状态、耗时；
4. 滚动右栏的**实时事件流/步骤**，展示每一步的 action（click / set_param / assert / screenshot）、执行结果、状态变化（hp/score）；
5. 指出第 3 步附近 `click #restart` 后 hp 异常。

【旁白】
> 「任务页左边是队列，能看到成功、失败、被中断的任务都如实保留。点开一个 42 步的全量回归：右边是完整的执行时间线。Agent 的每一个动作——点击、改参数、断言、截图——都记录在案，包括当时的血量、分数。注意第 3 步，点击重新开始之后，血量没有回到 100——这就是它抓到的第一个缺陷，而且每一步都能回放复现。」

---

### 镜头 4 · 缺陷证据链 + 代码定位（2:30–3:30，60s）

**画面**：在该任务详情里切到「缺陷/Bug」列表（或缺陷详情区）。

1. 依次展示 3 个缺陷：BUG-001 重开 HP 不重置（critical）、BUG-002 胜利页分数少 200（major）、BUG-003 alert 阻塞（major）；
2. 点开 BUG-001：展示严重度、结论（auto_confirmed）、证据通道（断言 + SDK 状态双通道）、来源步骤、截图数量；
3. 展开**修复建议**：根因列表、修复步骤、验证步骤、受影响模块、工作量/回归风险评级；
4. 强调「证据可审计」和「从结论到修法」两件事。

【旁白】
> 「这个任务发现了 3 个缺陷。以第一个为例：它不是一句『好像有 Bug』，而是带证据的——断言和 SDK 内部状态两个通道同时确认，发生在第 3 步，附带截图和可复现的操作序列。更关键的是，它直接给出修复方向：根因是重置路径漏了血量字段，建议把状态重置收敛到单一入口，并补一条回归断言，工作量和回归风险都标为低。从『发现 Bug』到『研发怎么修』，在同一个界面闭环。」

---

### 镜头 5 · 调度器与并发（3:30–4:05，35s）

**画面**：切到「系统」Tab。

1. 展示调度器状态、本机建议并发数（基于可用内存）；
2. 拖动并发滑块到超过建议值 → 出现橙色警告文案，再拖回来；
3. （可选，可不点）展示暂停/恢复/全部停止按钮，但**不要真的点停止**。

【旁白】
> 「系统页管并发。它会根据本机可用内存给出建议 worker 数，防止开太多浏览器把机器拖垮；超过建议值会明确告警。也可以一键暂停、恢复或停止全部任务。所有数据本地存储、任务在独立浏览器实例里跑，适合小团队内网或单机使用。」

---

### 镜头 6 · 现场复跑真实实验（4:05–4:45，40s，重头）

**画面**：Alt-Tab 切到第二个 PowerShell 终端（提前 cd 到项目根目录）。

现场执行（命令可提前粘贴好，录制时回车）：

```powershell
$env:PLAYWRIGHT_CHROMIUM_PATH="C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe"
C:\Users\hr173\miniforge3\python.exe tools\run_2048_cgroup.py
```

1. 等约 15–20 秒，屏幕依次打出 5 行 `✅ 发现`；
2. 跑完后滚动输出的表格：发现 5/5、Top-3 4/5、可操作 5/5、定位耗时几十到一百多毫秒；
3. （可选）用编辑器打开 `output\experiments\2048\c_group_report.md` 展示报告。

**容错**：若现场紧张，可提前跑好，直接展示报告文件 + 说"这条命令任何人都能复现"。但强烈建议真跑，5 个 ✅ 很有冲击力。

【旁白】
> 「光看 Demo 不够，我们在一个真实的第三方开源游戏 2048 上做了对照实验：往源码里注入 5 个真实缺陷，再让系统用浏览器加状态探针去盲测。现在现场复跑——五个缺陷，全部发现。其中四个代码定位进了前三候选，渲染类的直接给出可应用的 patch，纯静态定位只要一百毫秒左右。脚本和原始数据都在仓库里，评委可以自己复现。」

## 二、加分项（时间充裕可加，各 ~30s）

- **现场新建任务实时跑**：在「任务」Tab 新建一个指向 DemoGame 的任务（`file:///E:/AI造游戏大赛/playranger/examples/demo_game/index.html`），观察 queued → running、步骤实时增长。
  - 配了 LLM Key 时探索质量最好；
  - 没配 Key 会用内置 MockBrain，流程真实可看（真的会开浏览器去点），但不保证发现缺陷，旁白要说清"这是无 Key 时的保守策略大脑"。
  - 想看到浏览器窗口：用 `$env:PLAYRANGER_HEADLESS="0"` 后再启动 `demo_server.py`。
- **修复沙箱**：在缺陷详情里点「校验 patch」，展示 `git apply --check` 在隔离副本中的校验过程。
- **趋势报告**：浏览器打开 `output/demo/report_v2.html`，展示跨版本「新增/修复/遗留」差分。
